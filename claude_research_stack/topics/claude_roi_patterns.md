# Topic profile: Claude ROI patterns (hypothesis-driven)

This profile captures three high-ROI Claude deployment patterns as
**hypotheses to test**, not as verified facts. The numbers below were
supplied by the user from enterprise engineering / technical marketing
chatter and have **no primary citation attached**. The research loop's
job is to find one — or fail to and flag the gap.

The base research prompt (`prompts/master_routine.md`) already enforces
"prefer primary sources." This profile narrows the search and lists the
specific numbers that need sourcing.

## Topic string (paste into TOPIC env var or workflow_dispatch input)

```
Claude ROI patterns: locate primary-source evidence (Anthropic case
studies, customer case studies, vendor benchmarks, peer-reviewed
analyses) for three specific claims about high-ROI Claude deployments:
(1) Claude Code in enterprise growth engineering yielding ~4:1 ROI and
~45% CAC reduction, (2) Claude Agents + MCP shrinking technical SEO
audit time from ~8 hours to ~90 minutes, (3) Tool Search Tool reducing
per-message tool-context tokens by orders of magnitude vs. inlining
~55k tokens. For each claim, report: who published it, when, with what
methodology, and what counter-evidence exists.
```

## Claims under test

### Claim 1 — Claude Code in enterprise growth engineering

- **Asserted**: 4:1 ROI; ~45% reduction in Customer Acquisition Cost
  via automated personalized funnels.
- **Asserted setup**: Claude Code on the $100–200/mo Max tier
  (avoiding direct API over-billing) integrated into local terminal
  environments.
- **Asserted unit economics**: at $75/hour developer rate, "every
  PR generated by Claude Code costs ~$37.50 in AI spend."
- **What primary evidence would look like**:
  - An Anthropic customer case study naming the customer, the team
    size, the measurement window, and the baseline.
  - An enterprise engineering blog post (not a vendor reseller blog)
    with before/after metrics over a multi-month window.
  - A CAC delta that the customer's finance org confirmed, not just
    marketing.
- **Likely failure modes for the claim**:
  - Survivorship bias: only teams that succeeded write blogs.
  - "ROI" defined as developer-time-saved rather than incremental
    revenue. These are not the same number.
  - CAC reduction conflated with concurrent paid-marketing changes.

### Claim 2 — Claude Agents + MCP for technical SEO

- **Asserted**: Technical SEO audit time drops from ~8 hours to ~90
  minutes (≥80% reduction). Content briefs and refresh loops fully
  automated.
- **Asserted stack**: Claude Agents + MCP integrations with Google
  Search Console, Ahrefs, Semrush, WordPress, GitHub. Workflow loop:
  Gather → Act → Verify → Repeat.
- **What primary evidence would look like**:
  - A named SEO agency publishing per-client hours-saved figures
    with a defined audit checklist.
  - A vendor (Ahrefs, Semrush) benchmark naming the agent setup and
    the comparable manual workflow.
  - Independent reproductions on a defined website corpus.
- **Likely failure modes**:
  - "Audit" is undefined. An 8-hour audit and a 90-minute audit may
    not be the same scope of work.
  - Hours-saved on rote tasks ≠ outcomes-improved (rankings, traffic).
  - Vendor-published numbers are inherently biased; weigh accordingly.

### Claim 3 — Tool Search Tool vs. inlined tool context

- **Asserted**: Inlining ~55k tokens of tool definitions in every
  message vs. running a localized tool-search step → "massive" token
  cost reduction and improved call accuracy, "net-positive ROI
  despite slight added latency."
- **What primary evidence would look like**:
  - Anthropic engineering blog / docs explicitly comparing
    tool-search-first vs. inline-all-tools with token-count and
    accuracy numbers.
  - An MCP / Claude Developer Platform changelog entry that names the
    feature, its release date, and the published benchmark.
  - Independent benchmarks on a defined tool set (≥100 tools).
- **Likely failure modes**:
  - "55k+ tokens" is plausible for a sprawling multi-server setup but
    not universal. The right comparison is per-deployment, not
    abstract.
  - Latency cost of the extra search step is real and may erase
    savings for short-conversation, high-tool-density workloads.

## Source-type allowlist

Hard-restrict to primary sources:

- **Anthropic-published**: docs, engineering blog, changelog, customer
  case studies, papers, conference talks.
- **Customer-published**: blog posts on the customer's own domain
  with named authors and dates.
- **Independent benchmarks**: github.com/<org>/<benchmark-repo> with
  reproducible methodology.
- **Peer-reviewed**: arXiv preprints from named labs; conference
  papers (NeurIPS, ICML, EMNLP, ACL, USENIX, etc.).

## Disallowed

- LinkedIn posts, X/Twitter threads, Medium / Substack pieces unless
  they are the original author's own publication of their data.
- Re-aggregator blog posts ("top 10 Claude use cases") that cite no
  primaries.
- Vendor sponsored content that doesn't disclose sponsorship.

## Output additions on top of base RunOutput

- For each of the three claims, the source table must include a column
  noting whether the number is **traceable** (specific primary cited),
  **partial** (some primary, missing methodology), or **unsourced**
  (only secondary mentions).
- If a claim is **unsourced** after the run, raise a `Gap` row
  demanding a follow-up query and do not promote the claim into the
  synthesis.
